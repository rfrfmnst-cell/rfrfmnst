# ربط رفرف مع Tap عبر Supabase

## الحالة الفعلية

- نُشرت دالة `rafraf-tap`، الإصدار 2، في مشروع
  `gfxnwfjjpxmzvnylushd` بتاريخ 26 أكتوبر 2026.
- أُنشئ جدول `public.tap_payment_attempts` مع RLS وصلاحيات خادم فقط.
- فحص الصحة الحي أعاد 200، وطلب checkout دون اعتماد الخادم أعاد 401.
- webhook الحي أعاد `tap_not_configured`؛ إعدادات Tap في بيئة الدالة غير
  مكتملة. بعد إفادة المستخدم بإضافتها، أكد فحص الصحة أن أسماء المتغيرات الثلاثة
  لا تزال غير متاحة للدالة في هذا المشروع. لا يعرض الفحص قيم الأسرار. المفتاح
  المحفوظ في Hostinger لا ينتقل إلى Supabase تلقائيًا.
- أُعد كود الموقع لبدء الدفع عبر Supabase واستقبال نتيجته، لكنه لم يُنشر
  على استضافة الموقع ولم تُجرَ عملية دفع فعلية.
- قبول التحصيل الحي في الموقع مغلق حتى اكتمال دعم الاسترداد والمصالحة
  وتجربة قبول كاملة. لا تمثل هذه النسخة إطلاقًا إنتاجيًا للدفع.

## التصميم

يبقى نظام الطلبات الحالي في رفرف هو مصدر الملكية والمبلغ والحالة. لا تنقل
هذه الإضافة قاعدة الطلبات أو العملاء إلى Supabase ولا تنشئ حسابات بديلة.

1. يتحقق خادم الموقع من جلسة العميل وملكية الطلب وسياساته، ويحفظ محاولة
   `Payment` تحت الأقفال المالية الحالية قبل أي اتصال خارجي.
2. يستدعي الخادم Supabase بمفتاح خدمة خاص بالخادم. تُرسل هوية الطلب
   ومرجع المحاولة والمبلغ بالهللات وبيانات الدافع المطلوبة إلى Tap.
3. تحجز Supabase الطلب بفهرس فريد للمحاولات النشطة، وتستخدم مرجع المحاولة
   نفسه في `reference.idempotent` عند Tap. تُحفظ النتيجة غير المحسومة ولا
   تُعاد محاولة التحصيل آليًا بعد مهلة الشبكة.
4. تُنشئ الدالة صفحة Hosted Checkout باستخدام `src_all`، دون تمرير بيانات
   البطاقة عبر رفرف. تحفظ سجلًا للمحاولة دون ملف العميل أو بيانات البطاقة.
5. يصل إشعار Tap إلى Supabase. تتحقق الدالة من `hashstring` وفق عقد Tap،
   ثم تستعلم حالة التحصيل خادميًا وتطابق التاجر والوضع والمرجع والمبلغ وSAR.
6. ترسل Supabase نتيجة موقعة ومحددة الصلاحية إلى الموقع. يعيد الموقع
   الاستعلام من Supabase قبل تسوية الدفع والطلب ودفتر الضمان بمعاملة ذرية.
   العودة من المتصفح لا تثبت نجاح الدفع.

الدالة تستخدم تحققها الخاص: مسارات الخدمة تتطلب تطابق
`x-rafraf-service-key` مع مفتاح الخدمة الداخلي، ومسار Tap يتطلب توقيعًا
مستقلًا. لذلك `verify_jwt=false` مقصود، ولا يفتح checkout للعملاء.

## إعداد الأسرار

في [أسرار دوال مشروع رفرف](https://supabase.com/dashboard/project/gfxnwfjjpxmzvnylushd/functions/secrets)،
تُضاف القيم التالية سرًا، دون وضعها في المستودع أو المحادثة:

```dotenv
TAP_MODE=sandbox
TAP_SECRET_KEY=<مفتاح Tap التجريبي لحساب رفرف>
TAP_MERCHANT_ID=<معرّف تاجر رفرف>
TAP_CHECKOUT_ENABLED=true
TAP_LIVE_ENABLED=false
RAFRAF_SITE_ORIGIN=<أصل HTTPS لنسخة الاختبار>
```

لا تقبل الدالة مفتاح إنتاج بوضع sandbox. يوفّر Supabase متغيري
`SUPABASE_URL` و`SUPABASE_SERVICE_ROLE_KEY` للدالة تلقائيًا.

في بيئة **نسخة اختبار معزولة** للموقع، بعد نشر كود هذا الفرع:

```dotenv
PAYMENT_PROVIDER=tap
PAYMENT_MODE=sandbox
TAP_MODE=sandbox
SUPABASE_URL=https://gfxnwfjjpxmzvnylushd.supabase.co
SUPABASE_SERVICE_ROLE_KEY=<مفتاح الخدمة الخاص بمشروع رفرف>
CUSTOMER_PUBLIC_URL=<نفس أصل HTTPS لنسخة الاختبار>
```

الموقع يسمح بـsandbox في بيئة تطوير أو Vercel preview فقط، على غرار
حارس الإطلاق الحالي. يلزم استخدام قاعدة طلبات اختبار معزولة. لا تستخدم
`NEXT_PUBLIC_` لأي مفتاح خاص، ولا تمرر مفتاح الخدمة إلى المتصفح.
أدوات Supabase المتاحة في هذه الجلسة لا تدير أسرار Edge Functions، لذلك
إضافة الأسرار تحتاج لوحة المشروع أو CLI موثّقًا مسبقًا.

## المسارات

- صحة الخدمة: `GET /functions/v1/rafraf-tap/health`، دون بيانات حساسة.
- إعداد الخدمة: `POST /functions/v1/rafraf-tap/configuration`، للخادم فقط.
- بدء الدفع: `POST /functions/v1/rafraf-tap/checkout`، للخادم فقط.
- تأكيد الحالة: `POST /functions/v1/rafraf-tap/status`، للخادم فقط.
- إشعار Tap: `POST /functions/v1/rafraf-tap/webhook`، بتوقيع Tap.
- نقطة الموقع الموحدة: `POST /api/payments/checkout`، بجلسة العميل.
- إشعار الموقع الداخلي: `POST /api/payments/tap/webhook`، بتوقيع Supabase.

مسار EdfaPay السابق يبقى متاحًا، ويظل المزود الافتراضي ما لم يُضبط
`PAYMENT_PROVIDER=tap`. تستمر معالجة الدفعات القائمة بحسب مزودها.

## التحقق

```sh
node --test supabase/tests/*.test.mjs
```

نجحت 26 حالة اختبار محلية للاتصال، وتوقيع Tap، واعتماد خادم الموقع،
ومطابقة المبلغ والتاجر، وحجز محاولة متزامنة، والنتيجة غير المحسومة،
وإعادة الإشعار، ومنع تراجع الحالة، وحظر التحصيل الحي.

نجح بناء Next.js الكامل لتطبيق العميل وفحص TypeScript وتدقيق ESLint للملفات
المعدلة، ونجحت اختبارات قيود الجدول على قاعدة
Supabase بمعاملة أُلغيت بالكامل؛ لم تبقَ سجلات اختبار. أكدت مراجعة الصلاحيات
أن `anon` لا يقرأ الجدول وأن `authenticated` لا يكتب إليه. أبلغ مستشار الأمان
بملاحظة معلوماتية متوقعة عن عدم وجود سياسات وصول للعملاء؛ هذا الجدول للخادم
فقط، ولا توجد تحذيرات أمان أو أخطاء في المراجعة.

قبل فتح التحصيل الحي يلزم دعم الاسترداد والمصالحة والنزاعات في Tap واختبار
قاعدة الطلبات والضمان، ثم تنفيذ سيناريوهات sandbox بحساب رفرف: النجاح
والرفض والإلغاء وإغلاق المتصفح وتأخر الإشعار وتكراره وانقطاع الشبكة. لا
يمكن اعتبار الاختبارات المحاكية دليلًا على صحة مفاتيح الحساب أو اكتمال ذلك.
