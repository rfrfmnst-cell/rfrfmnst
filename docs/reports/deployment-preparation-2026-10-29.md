## خطوات التنفيذ بعد إتاحة اتصال الاستضافة

1. قراءة حساب الاستضافة والموقع المطابق تمامًا لكل نطاق، وخطة Node الحالية،
   ونوع التطبيق وربط النطاق وإعدادات Build وRuntime. لا إنشاء خطة مدفوعة.
2. قراءة المتغيرات المتاحة بشكل منقح، والتحقق الآمن من هدف PostgreSQL الأصلي
   وسر الجلسة المعتمد، ثم تجهيز اتصال فحص قراءة فقط. لا استبدال PostgreSQL
   بقاعدة MySQL التي قد تنشئها أدوات Hostinger العامة.
3. إثبات وجود نسخة ملفات وإعدادات سابقة قابلة للاستعادة وخطة رجوع على حساب
   Hostinger. لا تكفي حزمة Git للمصدر كنسخة احتياطية لبيانات المضيف.
4. مراجعة كل مجموعة متغيرات مع المحافظة على القيم الحالية. عملية استبدال
   بيئة Node قد تحذف كل مفتاح غير مرسل؛ القيم المقنعة ليست قيمًا صالحة
   لإعادتها إلى API. لا استبدال شامل دون توفر القيم الأصلية الآمنة.
5. رفع الحزم وتشغيل البناء بالإعدادات الصحيحة عند اكتمال شروط النشر.
   اسم bootstrap هو `hostinger-runtime/bootstrap.cjs`، والجذر والمخرجات
   `.` لهذه الأرشيفات. يحدد Hostinger PORT؛ مصدر البناء هو المرشح المثبت.
6. فحص هوية كل خدمة ومسارات الحياة، ثم readiness المحمية والمصادقة في
   بيئة الاختبار المعتمدة. نجاح صفحة HTTP 200 وحده لا يكفي لقبول النشر.

ترجع صفحة API العامة حاليًا إلى صفحة Hostinger الافتراضية؛ لا يكفي رفع
ملفات إلى موقع PHP دون ضبط مسار Node الصحيح. كما أن نقص بيئة العميل
واعتماد قاعدة الأعمال لم يُحسم بعد. حالة النشر الإنتاجي تبقى غير معتمدة
تقنيًا حتى تُفحص هذه المتطلبات وتنجح الفحوص ذات الصلة.

لم يُعد توليد روابط OAuth ذات رجوع localhost من البيئة البعيدة. الإجراء
المتبقي للوصول هو مصادقة موصل إدارة Hostinger من جهاز المالك ثم إثبات
إتاحة أدواته في هذه المحادثة؛ تفويض النشر موجود بالفعل، والعائق وصول تقني.
