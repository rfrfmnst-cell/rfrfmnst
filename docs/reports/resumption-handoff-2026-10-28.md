## الإصلاحات المنفذة في الاستئناف

### منع تجاوز حماية TLS بتغيير المضيف

الالتزام `90efbf15bee04fb302b96a6c8d49af30cb7fdc70` يرفض وسيط `host`
في query عنوان API. أثبت إنشاء pg Client دون فتح اتصال أن عنوان loopback
مع `host=db.example&sslmode=disable` يوجه المشغّل إلى خادم بعيد بلا TLS،
بينما كان الحارس يقبل العنوان. أصبح هذا التعارض مرفوضًا قبل إنشاء الحوض،
حتى عند ترميز اسم الوسيط أو تكراره. يبقى رفض تكرار `sslmode` واشتراط
`verify-full` للاتصال البعيد فعالين. لا تعطيل للتحقق من الشهادة.

## قاعدة البيانات الأصلية وحالة التشغيل

المصدر الحالي يربط Prisma في بوابات العميل والمورد والإدارة بـ`DATABASE_URL`،
ويعرّف `DIRECT_URL` لاتصال Prisma المباشر. API التشخيصية تستخدم
`API_DATABASE_URL` مستقلة لدور قراءة فقط. لا أيّ من هذه الاعتمادات أو أسرار
الجلسات متاح في بيئة المهمة؛ أكدت أداة البيئة عدم وجود bindings أسرار.
**لم يُحدد اسم مضيف قاعدة الأعمال أو اسمها الفعلي، ولم يُثبت اتصالها.**
إثبات أن الكود يستخدم PostgreSQL لا يعوّض غياب اعتماد الهدف الصحيح.

نُفذ استعلام كتالوج حقيقي في Supabase المعتمد داخل `BEGIN READ ONLY` ثم
`ROLLBACK`. بقي الجدول العام الوحيد `tap_payment_attempts`، مع RLS وFORCE
RLS ورفض SELECT لدوري anon وauthenticated. توجد ملاحظة INFO عن غياب سياسات
العميل لجدول خادم فقط؛
[مرجع المستشار](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).
هذا مشروع التكاملات، ولا يثبت أنه قاعدة حسابات المنصة. لا قاعدة بديلة أو
جداول حسابات أُنشئت فيه. روجعت تحديثات Supabase ذات الصلة دون تغيير المخطط.

أُعيدت طلبات GET العامة فقط؛ النتائج لم تتغير:

- حياة العميل والمورد والإدارة: 200. حياة API المنشورة: 404.
- صفحة دخول العميل: 200 مع رسالة عدم الإتاحة؛ لم تُرسل نماذج أو OTP.
- صحة Tap وOTO: 200، لكن متطلبات التهيئة غير متوفرة بحسب رايات الصحة؛
  OTO تصرح بأنها لا تنشئ شحنات. لم تُنفذ معاملات أو شحنات أو Sandbox غير معتمد.

## المتطلبات المتبقية قبل الاعتماد

1. توفير اتصال آمن بقاعدة الأعمال الأصلية بدور قراءة فقط، وهدف Staging
   وحسابات اختبار اصطناعية معتمدة، دون نشر الأسرار في المحادثة أو Git.
2. مطابقة هوية القاعدة ومخططها وقيودها وسجل migrations، ثم تشغيل readiness
   المحمية. العنوان البعيد يتطلب مضيفًا واضحًا و`sslmode=verify-full` مرة
   واحدة وشهادة موثوقة. لا `db push` أو `migrate deploy` أو seed في الإنتاج.
3. اختبار OTP الحقيقي والجلسات وMFA وإبطال الوصول وعزل العملاء والموردين
   على Staging؛ المحاكاة المحلية لا تثبت توصيل الرموز أو اتصال البيانات الحي.
4. تشخيص API المنشورة ورسالة دخول العميل من إعدادات وسجلات استضافة منقحة؛
   ثم تهيئة Tap/OTO Sandbox المعتمدة واختبار الإشعارات والتسوية الآمنة.
5. اختبار النسخ الاحتياطي والاستعادة والرجوع في بيئة معزولة، وتثبيت SHA
   المرشح، ثم طلب موافقة المالك قبل أي دمج أو نشر.

للاستكمال استخدم فرع PR #14، واقرأ ملف الأدلة وChecks قبل تعديل الكود.
التشغيل المعزول يتطلب Node 24 وpnpm 11.6.0 وتثبيت lockfile المجمد. الأوامر
`node scripts/audit-otp-expiry.mjs` و`node --test scripts/*.test.mjs supabase/tests/*.test.mjs`
لا ترسل OTP أو مدفوعات. مشغّل `node scripts/verify-site.mjs <site>` يجرد
أسرار التشغيل، ثم يُشغل اختبار قاعدة API المحلية بعد اكتمال بناء الحزمة.

كل إصلاح مكتمل محفوظ في التزام مستقل على فرع المرشح. سجلات التشغيل المحلية
موجودة في `outputs/verification/`، والملخص القابل للاستكمال مرفوع في ملف الأدلة.
بقي cache مولد `.turbo/` محليًا في نسخة الاسترداد دون حذفه أو رفعه؛ ليس تعديل
مصدر غير محفوظ. لا دمج في main أو نشر Hostinger أو تعديل إنتاج أو تعطيل SSL/RLS.
