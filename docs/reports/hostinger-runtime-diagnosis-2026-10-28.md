# تشخيص تشغيل رفرف على Hostinger — 28 أكتوبر 2026

**تنفيذيًا:** نطاق API يقدم صفحة PHP الافتراضية بدل خدمة Nest المتوقعة.
صفحة العميل تغلق الدخول برسالة عدم الإتاحة. تهيئة Tap وOTO في الدوال
المتصلة غير مكتملة. لم تتوفر جلسة مصادق عليها لإدارة استضافة Hostinger،
لذلك بقي تحديد قيم إعداداته وحالة قاعدة الأعمال الفعلية غير متحقق منهما.
لا تغيير للمصدر الذي اجتاز الاختبارات ولا إعدادات أو بيانات إنتاج.

المرشح المعتمد محفوظ كما هو:
[PR #14](https://github.com/rfrfmnst-cell/rfrfmnst/pull/14) عند
`734051d7d58d3fe0a4678d10ec309af8af19e670`.
هذا التقرير في فرع توثيق مستقل
`codex/rafraf-hostinger-diagnostics-20261028` مبني على ذلك الالتزام.
[الأدلة المنقحة](hostinger-runtime-evidence-2026-10-28.json) تحوي حالات HTTP
والترويسات المختارة ورايات الإعداد فقط؛ لا cookies أو أسرار أو محتوى بيانات أعمال.
الفحوص العامة تمت نحو **15:22 بتوقيت الرياض**، مع وقت UTC الدقيق في الأدلة.

هوية الإصدار العلنية قيمة بيئة معلنة، وليست بصمة كافية لإثبات تطابق ملفات

## سبب 404 لـAPI والإجراء المطلوب

السبب المثبت على مستوى الطلب العام هو **خدمة صفحة Hostinger الافتراضية
بواسطة PHP بدل خدمة API المتوقعة**. لا يعتمد `/api/liveness` في المرشح على
PostgreSQL أو أسرار المصادقة؛ لذلك غياب `DATABASE_URL` ليس تفسيرًا لهذا
الرد من الصفحة الافتراضية. لا يلزم إعادة كتابة Controller لحل هذه الملاحظة.

لتحديد إعداد hPanel المسؤول تحديدًا، يلزم قراءة سجل الموقع الذي يطابق
`api.rfrf.net` وحقول نوع الموقع وربط النطاق/التطبيق، ثم أحدث Build وإعداداته
ونقطة الدخول وسجلات Runtime. الاحتمالات غير المحسومة: موقع PHP بدل Node،
أو ربط النطاق بموقع آخر، أو غياب نشر تطبيق Node/اختيار مخرجاته الصحيحة.
لم تُقرأ هذه الحقول، فلا يمكن الجزم بأي واحد منها أو إصدار أمر إعادة تشغيل.

الإجراء التالي الآن: **قراءة الإعدادات والسجلات فقط** ومقارنتها بالجدول
أدناه. أي تغيير نوع الموقع أو ربطه أو بناء/نشر/إعادة تشغيل لاحق يحتاج
اعتماد المالك؛ لا يُحذف الموقع أو ملفات الصفحة الافتراضية أثناء التشخيص.

## سبب رسالة دخول العميل

المصدر عند المرشح يحسب:

```text
authAvailable = authenticationCoreConfigured() && !sessionUnavailable
authenticationCoreConfigured = DATABASE_URL غير فارغة && طول SESSION_SECRET >= 32
```

في طلب بلا `cu_auth`، تعيد `getSessionCustomerId()` القيمة null قبل استعلام
Prisma. لذلك، **إذا طابقت شيفرة النشرة الشيفرة المفحوصة**، فإن رسالة طلبنا
النظيف تشير إلى عدم تحقق شرط التهيئة: `DATABASE_URL` غائبة/فارغة، أو
`SESSION_SECRET` غائب/أقصر من 32، أو كلاهما. لا تحدد الاستجابة أيهما.
في طلب يحوي جلسة موقعة، يمكن لفشل استعلام الحساب أيضًا تفعيل
`sessionUnavailable`؛ هذا مسار مختلف لم يُختبر على حساب حقيقي.

هذا الفحص الأولي لا يتحقق من اتصال قاعدة البيانات أو Twilio، ولا يقرأ
`DIRECT_URL` أو `API_DATABASE_URL`. لذا لا يجوز نسبة الرسالة الحالية إلى
تعطل Twilio أو نقص API المنفصلة أو فشل اتصال PostgreSQL دون دليل آخر.
صلاحية صيغة سر الجلسة لا تثبت أنه السر الأصلي المعتمد؛ يلزم المحافظة عليه
لأن الكود يستخدمه أيضًا في تحقق كلمات المرور، وتدويره قرار مستقل.

المراجع داخل المرشح:

- `sites/rfrf.net/apps/customer/app/login/page.tsx`
- `sites/rfrf.net/apps/customer/lib/auth-configuration.ts`
- `sites/rfrf.net/apps/customer/lib/session.ts`

## مصدر PostgreSQL الأصلي

المثبت من المصدر: تطبيقات العميل والمورد والإدارة تنشئ PrismaClient من
`@rafraf/db`، ومصدر PostgreSQL في مخطط Prisma يقرأ `DATABASE_URL` و
`DIRECT_URL`. لا توجد عناوين اتصال فعلية غير اصطناعية في ملفات المصدر
والإعدادات المتتبعة التي فُحصت، ولا bindings أسرار متاحة في بيئة المهمة.
توجد أدوات قديمة للتحقق من هوية Neon، لكنها ليست إثباتًا أن حسابات
الإنتاج الحالية على مشروع Neon معين.

**اسم مضيف قاعدة الأعمال واسمها الفعلي غير محددين بعد.** يلزم استخراجهما
من إعداد العملية الفعلية في Hostinger أو مدير الأسرار المعتمد، داخل قناة
آمنة، مع مقارنة هوية الهدف بين البوابات الثلاث. لا يُرسل DSN في المحادثة.

أمكن تنفيذ استعلام كتالوج في Supabase المتصل ضمن `BEGIN READ ONLY` ثم
`ROLLBACK`: الجدول العام الوحيد هو `tap_payment_attempts`، مع RLS وFORCE
RLS. لم تُقرأ صفوف حسابات أو طلبات. هذا دليل على مشروع التكاملات، ولا
يثبت أنه قاعدة الأعمال ولا أن بيانات الحسابات مفقودة. لا إنشاء قاعدة أو
جداول بديلة ولا migrations أو seed أو provisioning.

## مصفوفة المتغيرات: ما يُعرف وما يلزم

حالة «غير متحقق» أدناه تخص **عملية Hostinger**. غياب المتغير من بيئة
Codex لا يثبت غيابه من الاستضافة، ووجود اسم مقنّع في hPanel لا يثبت صلاحية
قيمته أو وصول العملية إليه.

| المتغير/النطاق | حالة الاستضافة المثبتة | التحقق المطلوب دون كشف القيمة | الإجراء بعد تحديد النقص |
| --- | --- | --- | --- |
| `DATABASE_URL` — البوابات الثلاث | غير متحقق؛ شرط إتاحة العميل لا يمر وفق المصدر المفحوص | وجود غير فارغ، صيغة PostgreSQL، هوية قاعدة الأعمال، TLS وشهادة موثوقة، دور التشغيل الصحيح | مسؤول القاعدة يربط اعتماد المنصة الأصلي عبر مدير الأسرار؛ لا قاعدة جديدة |
| `DIRECT_URL` — Prisma للبوابات | غير متحقق؛ ليس شرط رسالة الدخول | وجود وصيغة صحيحة عند الحاجة لأوامر Prisma، ومطابقة هدف قاعدة الأعمال، مع مراعاة أن pooled/direct قد يختلف مضيفاهما | توثيق الاتصال المباشر الآمن؛ لا تشغيل migrations في الإنتاج أثناء التشخيص |
| `SESSION_SECRET` — العميل والمورد | غير متحقق؛ مرشح سبب الرسالة | وجود وطول بعد trim لا يقل عن 32، ومطابقته للسر المعتمد دون طباعته أو حفظ بصمته | إعادة ربط السر الأصلي إن كان مفقودًا؛ التدوير يحتاج تقييمًا مستقلاً |
| `ADMIN_SESSION_SECRET` — الإدارة | غير متحقق | وجود وطول لا يقل عن 32، مع MFA الفعلي | ربط السر الإداري المعتمد وإعداد Twilio المخصص؛ HTTP 200 ليس إثباتًا |
| `API_DATABASE_URL` — API | غير متحقق؛ المعالج العام الحالي PHP | DSN مستقل للهدف الأصلي بدور قراءة فقط، `sslmode=verify-full` مرة واحدة، دون وسيط host متعارض، وشهادة موثوقة | تجهيزه في بيئة اختبار معتمدة ثم استدعاء readiness المحمي؛ لا إعادة استعمال دور كتابة تلقائيًا |
| `READINESS_PROBE_SECRET` — API | غير متحقق | وجود وطول 32–512، خادمي فقط | تخزينه آمنًا واستعماله في ترويسة الفحص دون تسجيله |
| متغيرات Twilio — العميل/المورد/الإدارة | غير متحقق | `TWILIO_ACCOUNT_SID` و`TWILIO_API_KEY_SID` و`TWILIO_API_KEY_SECRET` و`VERIFY_SERVICE_SID` بصيغة صحيحة ومن الخدمة المأذونة | اختبار Staging وحسابات اصطناعية؛ لا إرسال OTP إلى مستخدمين حقيقيين |

لا يُنسخ sslmode الخاص بـPrisma آليًا إلى pg؛ لكل مشغل صيغه المدعومة.
حارس API الخاص بـpg يفرض verify-full. يجب إبقاء تحقق الشهادة وRLS فعالين.

## متطلبات Tap Sandbox

الفحص الحي لـ`rafraf-tap/health` يعرض غياب مفتاح التاجر ومعرفه ووضع صحيح.
هذه نواقص مؤكدة للدالة المتصلة، لا تخمينًا بشأن Hostinger.

1. في أسرار **دوال Supabase المعتمدة**: `TAP_MODE=sandbox`، مفتاح اختبار
   Tap الحقيقي من حساب رفرف، `TAP_MERCHANT_ID`، و`RAFRAF_SITE_ORIGIN` لبيئة
   Staging. المفتاح المطلوب يبدأ ببادئة اختبار Tap؛ لا يُنسخ في التقرير.
2. تبقى `TAP_LIVE_ENABLED=false`. تفعيل `TAP_CHECKOUT_ENABLED=true` إجراء
   لاحق في Staging فقط بعد إعداد الاعتمادات والاختبار المعتمد.
3. في عملية العميل على Staging: `PAYMENT_PROVIDER=tap` و
   `PAYMENT_MODE=sandbox` و`TAP_MODE=sandbox` و`CUSTOMER_PUBLIC_URL` الصحيح،
   ثم `SUPABASE_URL` للمشروع المعتمد و`SUPABASE_SERVICE_ROLE_KEY` خادمي فقط.
   لا تُنسخ الأسرار بين Hostinger وSupabase تلقائيًا ولا توضع في NEXT_PUBLIC.
4. حارس الشيفرة الحالي يتطلب بيئة preview؛ عند تشغيل Staging منفصلة بإعداد
   إنتاج Node، فإن `VERCEL_ENV=preview` هو المؤشر الذي يقرأه الحارس. هذا
   وصف لشرط الكود وليس إذنًا بتغيير نطاق الإنتاج أو تجاوز الحارس عليه.
5. التحقق لاحقًا من إشعار Tap الموقّع وإشعار الجسر الداخلي ومطابقة المبلغ
   والتاجر والطلب، والرفض والإلغاء والتكرار وتأخر الإشعار والمصالحة. لا
   تحصيل حي أو استرداد فعلي أو فتح إطلاق إنتاجي ضمن هذه المرحلة.

## متطلبات OTO Sandbox

فحص الدالة المتصلة يثبت `tokenPresent=false` و`enabled=false` و
`automaticShipmentDisabled=false` و`configured=false`، مع
`createsShipments=false`. الراية الثالثة تعني أن قفلي تعطيل الشحن الصريحين
غير مكتملين؛ لا تعني أن الدالة تنشئ شحنات الآن.

- يلزم حساب/اعتماد تجريبي **تؤكده OTO** قبل أي اتصال مزود؛ لا يوجد في
  الكود الحالي مفتاح إعداد عام يحول عنوان OTO إلى Sandbox تلقائيًا.
  المسار الحالي للاتصال يستعمل `api.tryoto.com`؛ لا يُعتبر تجريبيًا لمجرد
  ضبط OTO_ENABLED. إذا لم يؤكد المزود صلاحية الاختبار هناك، تستمر المحاكاة فقط.
- في بيئة الاختبار المعتمدة للدالة: `OTO_REFRESH_TOKEN` الاختباري، و
  `OTO_ENABLED=true`، و`OTO_AUTO_CREATE_SHIPMENT=false` و
  `SHIPMENT_AUTO_CREATE=false` صراحة. لا تغيير في هذه الجلسة.
- لربط إدارة Staging بالجسر: `OTO_TRANSPORT=supabase` و`SUPABASE_URL`
  و`SUPABASE_SERVICE_ROLE_KEY` الخادمي. لا يُستبدل النقل الحالي قبل اعتماده.
- الاختبارات التالية المسموحة عند الاعتماد: المصادقة وhealthCheck والأسعار
  ومعاينة draft محلية؛ لا createOrder أو createShipment أو بوليصة أو شراء رصيد.

## حدود الوصول والإجراء التنفيذي التالي

أدوات Hostinger المتاحة في هذه الجلسة للبريد فقط. لم يوجد اتصال إدارة
استضافة مسجل عند البداية، ولا HOSTINGER_API_TOKEN أو اعتماد قاعدة أو
Staging في بيئة المهمة. أُضيف تعريف MCP المحلي الرسمي
`https://mcp.hostinger.com` دون أسرار؛ بدأ OAuth لكنه لم يكتمل، ولم تصبح
عمليات قراءة المواقع والمتغيرات والسجلات متاحة في الجلسة الحالية.
هذه إضافة إعداد محلي، وليست تغييرًا لحساب Hostinger أو إعدادات المواقع.

لاستكمال قراءة hPanel يلزم ربط إدارة الاستضافة بحساب المالك عبر نافذة
تسجيل الدخول الرسمية، ثم إتاحة أدواتها في جلسة جديدة. لا يلزم إرسال كلمة
مرور أو مفتاح في المحادثة. موصل البريد وحده لا يوفر هذا الوصول.

| الأولوية | المسؤول/الإجراء | مخرج القبول |
| --- | --- | --- |
| P0 | ربط اتصال إدارة الاستضافة للقراءة | قائمة المواقع الأربعة ونوع كل تطبيق وربط نطاقه، دون أسرار |
| P0 | قراءة إعداد API وأحدث Build وRuntime | تحديد حقل الربط/النوع/المخرجات المسؤول عن صفحة PHP الافتراضية |
| P0 | فحص وجود وصلاحية متغيرات عملية العميل بشكل منقح | حسم DATABASE_URL أم SESSION_SECRET، ثم تحديد هوية قاعدة الأعمال |
| P1 | توفير وصول قاعدة أصلي بدور قراءة فقط وهدف Staging | TLS موثق وهوية قاعدة ومخطط وصلاحيات كتالوج؛ لا قراءة بيانات شخصية |
| P1 | اختبار المصادقة والجلسات وMFA في Staging | حالات دخول وOTP وصلاحيات مثبتة بحسابات اصطناعية |
| P2 | تهيئة Tap وOTO التجريبية المعتمدة | اختبارات جسر ومحاكاة/اختبار مزود مأذون بلا معاملات أو شحنات حقيقية |

لم تُشغل أدوات provisioning أو seed أو verify-runtime-connection على قاعدة
حية: بعضها يختبر الكتابة وDDL حتى مع rollback، فلا يلائم تشخيص القراءة
فقط. لم تُعد اختبارات البناء التي نجحت للمرشح لأنه لم تتغير أي شيفرة تشغيل.
اختبارات هذه الدفعة هي GET العامة واستعلام الكتالوج للقراءة ومراجعة المصدر
والإعداد المحلي للموصل. لا دمج أو نشر أو إعادة تشغيل أو حذف ملفات أو بيانات.
