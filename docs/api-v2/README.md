- `sites/api.rfrf.net/apps/api/src` تطبيق Nest يقدّم `/` و`/api/liveness`
  ووثائق OpenAPI المحكومة ببيئة التشغيل. لا يحتوي واجهات الأعمال الحالية.
- العميل والمورد والإدارة تطبيقات Next مستقلة تتصل عبر Prisma بقاعدة المنصة.
  مخططات Prisma الثلاثة متطابقة وقت المراجعة. لا تنقل البيانات إلى قاعدة جديدة.
- Supabase يستخدم الآن لوسيط Tap وOTO وجدول محاولات Tap فقط. ليس مصدر
  حسابات العملاء أو الموردين أو الطلبات، ولا تُنشأ حسابات Supabase Auth بديلة.
- تُراجع إصلاحات PR #9 والاختبارات في فرع الإصلاحات بشكل مستقل. تُعتمد
  الوحدات الصالحة بعد اختبارات التطابق؛ لا تُنسخ snapshots كاملة فوق مصدر أحدث.

## القرار المعماري

تركيب `V2Module` لاحقًا تحت `/v2`، مع إبقاء التطبيق القديم ومسارات Next
والـwebhooks الحالية. تستخدم تطبيقات Next طبقة BFF على الخادم؛ لا توسيع
نطاق كوكي الجلسة إلى جميع النطاقات الفرعية ولا كشف مفاتيح الخدمة للمتصفح.

يقرأ adapter المصادقة الجلسة الحالية الموقعة ويعيد فحص حالة الحساب والدور
والصلاحيات في قاعدة المنصة. يجب أن يكون التوكِن مقيّدًا بالجهة والجمهور
ومدة قصيرة وnonce عند تمريره من BFF إلى API؛ لا يُعد ترويس `supplierId`
أو دور يرسله العميل أو CORS إثبات هوية. اعتماد هذا البروتوكول وتدوير مفاتيحه
وإبطال جلساته شرط قبل أي مسار خاص. لا إصدار توكنات غير مدعوم بعقد مُختبر.

تفصل الوحدات: Identity وSuppliers وCatalog وRFQ وQuotes وOrders وPayments
وShipping وAudit. تبدأ النقل بوظائف القراءة، وتبقى الكتابة لدى المالك القديم
حتى نجاح المقارنة. لا dual-write ولا side effects في shadow traffic.

## إعادة استخدام الوحدات الحالية

| المجال | المصدر الحالي المرشح | شرط النقل |
| --- | --- | --- |
| العملاء وOTP | `sites/rfrf.net/apps/customer/lib/customer-auth-service.ts` و`session.ts` | إعادة فحص انتهاء OTP بعد مزود الخدمة، ومنع replay وتعطيل المستخدم |
| الموردون | `sites/supplier.rfrf.net/apps/supplier/lib/session-access.ts` و`app/login/actions.ts` | حالة المورد وملكية كل صف؛ لا تعتمد JWT وحده |
| الصلاحيات والتسعير | `packages/shared/src/security` و`pricing` داخل الحزم | حظر التكاليف وهوية المورد على استجابات العميل وحظر الهامش على المورد |
| الطلبات | `sites/rfrf.net/packages/orders` و`packages/shared/src/workflow` | معاملات وأقفال وانتقالات الحالة الحالية دون تغيير قواعد العمل |

المسارات أعلاه نقاط بدء للمراجعة وليست موافقة على نشرها أو استبدالها.

## العقد الأولي

`openapi.json` مسودة OpenAPI 3.0.3. كل المسارات الخاصة افتراضيًا مغلقة؛
اسم `BffSession` يصف البروتوكول المطلوب ولا يثبت تنفيذه. أمثلة الأدوار
والمعرفات اصطناعية. لا يربط العقد مفاتيح أو عناوين إنتاج.

- `GET /v2/health`: حياة العملية فقط دون قاعدة أو أسرار.
- `GET /v2/me`: هوية ودور وصلاحيات من الخادم، دون claims قابلة للتعديل.
- `GET /v2/orders`: صفحة طلبات يحدها الدور والملكية، دون تكلفة/هامش داخلي.
- `GET /v2/orders/{orderId}`: فحص ملكية في الاستعلام نفسه؛ 404 موحد للمفقود
  وغير المملوك. صلاحية الإدارة مطلوبة ولا تكفي تسمية الدور وحدها.
- أوامر RFQ والعروض وقبول الطلب والتحصيل والشحن مؤجلة إلى عقد لاحق؛
  كتابة مالية أو شحن تحتاج `Idempotency-Key` مقيّدة بالممثل والأمر وبصمة
  المدخلات، وحجزًا دائمًا ذريًا قبل المزود. لا retry بعد نتيجة مالية مجهولة.

كل مبلغ عدد صحيح بالهللات مع `SAR`، والتاريخ UTC بصيغة ISO8601،
والترقيم cursor opaque وحدود ثابتة. الأخطاء برمز ثابت وrequestId دون
stack أو رسائل Prisma أو محتوى مزود. correlationId ينشئه الخادم ولا يستخدم
لقرارات التفويض. تخصيص DTO لكل دور؛ لا إعادة كائن Prisma إلى المتصفح.

## البيانات والانتقال والرجوع

1. جرد كل route وServer Action ومن يملكه واختبار سلوكه وDTO وصلاحياته.
2. تفعيل `/v2/health` فقط بعد اختبار Nest محليًا، دون تبديل مستهلك.
3. تجهيز adapter الهوية ضد قاعدة اختبار معزولة، واختبارات عاملين متزامنين
   لانتهاء/تكرار OTP وقفل الحساب والتبديل بين بوابة العميل والمورد والإدارة.
4. نقل قراءة الطلبات خلف علم افتراضي مغلق؛ مقارنة DTO بالمسار القديم
   ببيانات اصطناعية، مع اختبارات IDOR وعزل موردين وعميلين وصلاحيات الإدارة.
5. نقل أوامر الأعمال واحدًا بعد الآخر بعد إثبات المعاملات والأقفال والتكرار.
   ممنوع استدعاء مزود أثناء قفل طويل أو تسوية دفع من عودة المتصفح.
6. تجربة staging مستقلة وموافقة المالك قبل أي تحويل إنتاج. تعطيل العلم
   يعيد المستهلك فورًا إلى المسار السابق. لا إسقاط جداول أو إزالة مسارات
   قبل انتهاء فترة التوافق ووجود سجل قبول كامل وخطة استعادة مختبرة.

لا migration لازمة لهذه المسودة. أي تعديل لاحق للمخطط يكون additive مع
rollback ومراجعة RLS/GRANT، ولا يُطبّق على الإنتاج دون موافقة محددة.

## شروط القبول قبل التنفيذ أو النشر

- اختبار عقود إيجابي وسلبي لكل DTO ودور، بما فيها الحقول المحظورة.
- TypeScript وLint وJest وHTTP e2e وبناء Hostinger وتشغيل runtime معزول.
- PostgreSQL اختبار: معاملات حقيقية وأقفال وتكرار وrollback وقيود FK،
  دون استعمال قاعدة إنتاج. بيانات العملاء والموردين الأصلية غير متحقق منها.
- Tap sandbox: نجاح ورفض وإلغاء وتكرار webhook وتأخره وانقطاع الشبكة؛
  حظر live وعدم تكرار التحصيل. OTO mocks/حساب اختبار موثق دون شحنة فعلية.
- فحص سجلات منقحة وحدود معدل وأصول وثقة proxy وحجم body، ومؤشرات مراقبة
  تبين الأخطاء وزمن الاستجابة دون بيانات شخصية.
- لا تعتبر قراءة OpenAPI أو نجاح JSON تحققًا من تنفيذ المسارات؛ التنفيذ
  واختبارات قبولها ما زالا مطلوبين.
