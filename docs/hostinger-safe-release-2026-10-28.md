# خطة نشر رفرف والرجوع الآمن — 28 أكتوبر 2026

الحالة: خطة للمراجعة فقط. لم يحدث رفع أو نشر أو تغيير DNS أو قاعدة إنتاج.
لا تتوفر في هذه الجلسة أدوات حساب استضافة Hostinger موثقة؛ لذلك إعداداته
الحالية والنسخ الاحتياطية على المضيف **غير متحقق منها**. أدوات البريد لا
تثبت اتصال لوحة الاستضافة. القيم أدناه مبنية على ملفات `MANAGED_HOSTINGER.md`.

## بوابات الموافقة

1. مراجعة PR الإصلاحات ونتائج CI، وتحديد SHA المرشح. إبقاء API V2 خارج
   إصدار الإصلاحات حتى اكتمال اختبار التوافق؛ الـAPI القديم يبقى كما هو.
2. بيئة staging منفصلة لكل تطبيق وقاعدة PostgreSQL اختبار ببيانات اصطناعية،
   وتخزين خاص منفصل. لا نسخ بيانات شخصية أو أسرار إنتاج إلى اختبارات CI.
3. تفعيل مزودي sandbox المعتمدين فقط في staging، مع إيقاف التحصيل الحي
   والشحن الآلي وشراء البوالص. لا ترسل OTP إلى أرقام العملاء للاختبار.
4. لا دمج في `main` ولا نشر إنتاج ولا migration قبل موافقة المالك على
   العملية والهدف المحددين. لا تربط هذا PR بنشر تلقائي إلى الإنتاج.

## الجرد والنسخ الاحتياطي قبل أي نشر

- توثيق ربط النطاقات الأربعة بالمشاريع ومجلدات الجذر وأوامر البناء، والتحقق
  من SSL ومن عدم وجود webhook ينشر الفروع تلقائيًا. لا تغيير DNS مطلوب.
- حفظ الإصدار العامل ومصدره وأصوله وملف إعداد التشغيل في مخزن مشفر محدود
  الصلاحيات؛ تسجيل بصمات الملفات دون قيم الأسرار في تقرير الإصدار.
- أخذ snapshot معتمدة من مزود PostgreSQL الأساسي، ونسخة متسقة قابلة
  للاستعادة من قاعدة التكامل في Supabase. اختبار الاستعادة في قاعدة معزولة.
- نسخ التخزين الخاص للوثائق وأدلة الطلبات مع صلاحياته وملكيته وبصماته.
  إثبات مشاركة واستمرار مسارات التخزين بين التطبيقات بعد إعادة النشر.
- تحديد مسؤول الرجوع ونافذة النشر وزمن الاستعادة المقبول. لا يبدأ النشر
  إذا غابت نسخة احتياطية مجربة أو تعذر الرجوع إلى الإصدار السابق.

## إعداد التشغيل المراد التحقق منه

| التطبيق | المصدر | البناء | الدخول |
| --- | --- | --- | --- |
| العميل | `sites/rfrf.net` | `pnpm build` | `hostinger-runtime/bootstrap.cjs` |
| المورد | `sites/supplier.rfrf.net` | `pnpm build` | `hostinger-runtime/bootstrap.cjs` |
| الإدارة | `sites/admin.rfrf.net` | `pnpm build` | `hostinger-runtime/bootstrap.cjs` |
| API | `sites/api.rfrf.net` | `pnpm build` | `hostinger-runtime/bootstrap.cjs` |

- Node.js 24 وpnpm 11.6.0، و`pnpm install --frozen-lockfile` في مجلد كل
  تطبيق. نوع التطبيق Express، الجذر والمخرجات `.` وفق الحزم الحالية.
- `NODE_ENV=production`، و`PORT` الذي يوفره Hostinger، و`HOSTNAME=0.0.0.0`
  لتطبيقات Next. ضبط `RAFRAF_RELEASE_SHA` على SHA المرشح.
- الأصول العامة `CUSTOMER_PUBLIC_URL` و`ADMIN_PUBLIC_URL` وأصل المورد
  وقائمة `API_ALLOWED_ORIGINS` مطابقة لنطاقات البيئة. تغيير `NEXT_PUBLIC_*`
  يحتاج إعادة بناء. لا مفتاح خاص تحت هذا الاسم.
- قاعدة المنصة الأصلية عبر `DATABASE_URL` بدور تشغيل محدود، ومطابقة
  نسخ Prisma والمخطط. `DIRECT_URL` لأداة إدارة مصرح بها فقط؛ لا تشغيل
  `seed` أو `migrate dev` أو `db push` في الإنتاج. هذا الإصدار لا يحتاج migration.
- `SESSION_SECRET` و`ADMIN_SESSION_SECRET` مستقلان وقويان وثابتان بين
  النسخ؛ لا تبدلهما ضمن النشر دون خطة إنهاء جلسات معتمدة.
- إعداد Turnstile والأصول المسموحة وResend/SMTP وTwilio Verify وMFA
  وفق البيئة. تعطيل OTP المحلي في الإنتاج. غياب الإعداد يبقي الدخول مغلقًا.
- التخزين خاص ودائم؛ `STORAGE_PROVIDER=local` ليس تخزين إنتاج. تأكيد
  إعداد Supabase على الخادم فقط، وعدم الخلط بين قاعدة التكامل وقاعدة المنصة.
- إبقاء بوابات الدفع والشحن الحي مغلقة إلى أن تُثبت sandbox والـwebhooks
  والتطابق المالي والمصالحة والاسترداد وعزل شحنات الموردين.

## تجربة staging وقبول الإصدار

تشغيل `node scripts/verify-site.mjs <site>` من نسخة نظيفة بلا ملفات أسرار،
ثم تشغيل اختبارات المتصفح محليًا على الحزم الناتجة. يحذف مشغّل التحقق
اعتمادات الخدمات من بيئة أبنائه؛ لا تستخدمه كأداة نشر أو فحص إنتاج.

في staging المهيأة، يلزم إثبات التسجيل والبريد وOTP الصحيح والخاطئ والمنتهي
والمكرر، بقاء الجلسات وإنهاؤها، حظر المستخدم المعطل والمورد الموقوف، عزل
حسابين مختلفين، ومصادقة الإدارة الثنائية والصلاحيات. اختبار دورة طلب
اصطناعي كاملة حتى التسليم، وعدم كشف تكلفة داخلية للعميل أو هامش للمورد.
فحص العربية وRTL ولوحات المفاتيح و320/390/768/1440 بكسل ورفع الملفات الخاص.

بعد الموافقة على الإنتاج: نشر الحزم المجربة نفسها تدريجيًا، والتحقق من
`/api/liveness` وSHA والأصول الثابتة ووجهات الدخول وترويسات الحماية، ثم
فحص جلسة اختبار معتمدة دون دفع أو شحن. مراقبة أخطاء 5xx والمصادقة والاتصال
بقاعدة البيانات والسجلات المنقحة. لا يعد HTTP 200 دليلًا على نجاح تسجيل الدخول.

## الرجوع

عند فقد دخول أو خلل صلاحيات أو زيادة أخطاء: إيقاف توسعة النشر وتفعيل وضع
الصيانة عند الحاجة، وإعادة الحزمة السابقة وإعداداتها المعتمدة على التطبيقات
المتأثرة. تثبيت `RAFRAF_RELEASE_SHA` السابق وإعادة فحوص الحياة والأصول
والمصادقة. عدم إعادة استعمال مخرجات بناء فاشلة.

لا تُستعاد قاعدة البيانات تلقائيًا عند رجوع الكود: قد تحتوي طلبات صحيحة
أُنشئت بعد النشر. هذا الإصدار لا يغيّر المخطط. عند فساد بيانات مثبت، تجميد
الكتابة وحفظ snapshot للحالة المتضررة ومقارنة السجلات وتجهيز استعادة أو
تصحيح انتقائي معتمد. لا حذف طلبات أو وثائق ولا تغيير أسرار ولا DNS ضمن
خطة الرجوع دون موافقة محددة.
