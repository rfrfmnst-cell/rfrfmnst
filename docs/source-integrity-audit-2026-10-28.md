تاريخ الفحص: 2026-10-28
الغرض: توثيق تغطية ملفات التطبيقات الأربعة ومصادر Hostinger وGitHub قبل
استعادة ملفات أو إنشاء وحدات جديدة. هذا التقرير لا يجيز دمج PR أو النشر.

## خلاصة الجرد

لم يظهر ملف مصدر متتبع في snapshots المستوردة من Hostinger مفقودًا من
`origin/main` أو من شجرة PR #9 عند المقارنة بالمسار. لا توجد، بناءً على هذه
المقارنة، ملفات أصلية متاحة تحتاج إلى إعادة إنشاء.

تعرّف ملفات `MANAGED_HOSTINGER.md` المصدر المرجعي لكل نسخة بأنه
`mubasatplatform-debug/rafraf@main` عند
`795d4d5121f73404141c0a53ead450216b30f7b7`. تعذر فتح المستودع الخارجي
عبر GitHub API (404)، لذلك يثبت هذا الفحص تغطية ملفات commits المستوردة
في هذا المستودع، لا التطابق بايتًا ببايت مع المستودع الخارجي أو مع ملفات
موجودة على حساب Hostinger.

## اختلاف مهم في PR #9

شجرة PR #9 ليست بديلًا مطابقًا لـ`main` الحالي. المقارنة المباشرة مع
`origin/main` أظهرت حذف ميزات أُضيفت بعد snapshot Hostinger، منها:

- في العميل: `apps/customer/app/api/payments/checkout/route.ts`،
  و`apps/customer/app/api/payments/tap/webhook/route.ts`،
  و`apps/customer/lib/payments/tap-launch.ts`،
  و`apps/customer/lib/payments/tap-supabase-provider.ts`.
- في الإدارة: `apps/admin/lib/shipping/oto-supabase.ts`.
- تكامل Tap/OTO المشارك: وظائف Supabase، سجل محاولات Tap وترحيله،
  الاختبارات، وملفات توثيق التكامل. هذه الملفات موجودة على `main` وليست
  ضمن ملفات Hostinger الأصلية المستوردة.
- حُذفت أيضًا ملفات موافقة Google الاختيارية؛ وهي ليست ضمن نطاق استعادة
  وظائف الطلبات أو الدفع.

لم تُنسخ هذه الملفات فوق PR #9 ولم تُعدّل فروع PR #9 أو PR #10. استعادتها
داخل شجرة PR #9 ستتداخل مع تعديل مسار الدفع وملفات `oto.ts` الحالية؛ يلزم
قرار ومراجعة مستقلة قبل أي تسوية. PR #10 تصميم وعقد API V2 فقط، وليس تطبيقًا
جديدًا أو إصلاحًا لملفات API الحالية.

## API وقاعدة البيانات

- توثّق `sites/api.rfrf.net/MANAGED_HOSTINGER.md` أن API المنفصلة تنفذ
  `/` و`/api/liveness` فقط، ولا تتضمن قاعدة بيانات أو مسارات أعمال. وجود
  وحدات العملاء والمورد والإدارة ضمن تطبيقات Next/BFF هو الوضع الموثق؛ لذلك
  لم تُنشأ وحدات API أو migrations مفترضة.
- مخططات Prisma لدى العميل والمورد والإدارة متطابقة في `origin/main`:
  Git blob موحد `2ec0a11117948a8b5574dbbd23aa9f5d2b0bb687`.
- لم يُفتح اتصال بقاعدة الإنتاج، ولم تُشغّل migrations أو seed أو تعديل
  بيانات.

## استثناءات الحزم

تستبعد `.gitignore` لكل تطبيق عمدًا `node_modules/` و`.next/` و`dist/`
و`build/` وملفات `.env*`؛ ليست ملفات مصدر ناقصة. ملفات البيئة والأسرار
تُجهّز خارج الحزم. لا يثبت وجود الشيفرة وحده إعداد الخدمات أو قبول التشغيل.

## اختبارات هذه الجولة

- العميل: 24 اختبار وحدة ناجحًا للمصادقة/OTP، البحث وإدخال القطع، كتالوج
  المركبات، وVIN.
- المورد: 19 اختبار وحدة ناجحًا للمصادقة/OTP والصلاحيات والهاتف واستيراد
  الكتالوج.
- الإدارة: 5 اختبارات لمسارات الدخول وفق الصلاحيات.
- QA العام: 11 اختبارًا.
- Tap وOTO: 34 اختبارًا مع fixtures ومحاكاة داخل الذاكرة؛ لا اتصال بمزود
  ولا معاملة مالية.
- API: لم يكتمل تشغيل Jest في بيئة الفحص؛ فشل حل `@nestjs/testing` من
  مجلد اختبارات e2e رغم إعلانه في manifest. لا يثبت ذلك فشل بناء API.

أُعيدت محاولة بناء العميل: نجح تجميع Next وفحص TypeScript وإنشاء الصفحات
الثابتة، لكن مرحلة `Collecting build traces` استمرت باستهلاك موارد؛ أُوقف
الأمر لتجنب استمرار تعليق بيئة التطوير. سجل تحقق سابق للبناء في هذه الجلسة
كان قد أثبت نجاح بناء العميل والمورد والإدارة وNest API، لكن لم تكتمل إعادة
تشغيل الأبنية الأربعة في هذه الجولة.

## متطلبات تشغيل لم تُتحقق

- العميل والمورد: اتصال قاعدة المنصة المعتمدة، `SESSION_SECRET` قوي،
  ومزودو OTP/البريد/التخزين اللازمون لمسارات الاستخدام المختبرة.
- الإدارة: قاعدة المنصة، `ADMIN_SESSION_SECRET`، ومزود MFA معتمد
  وصلاحيات حساب إدارة.
- Tap: مفاتيح ومعرف تاجر Sandbox وwebhook مضبوط واختبار status حقيقي
  عند موافقة المالك وتوفر بيانات Sandbox؛ لم يُستخدم أي مفتاح.
- OTO: رمز تحديث وبيانات webhook وموقع استلام وإعداد إيقاف الإنشاء التلقائي؛
  لم يُرسل رمز ولم يُنشأ شحن.

لا تغيير في الكود التشغيلي أو إعداد قاعدة البيانات أو الأسرار، ولا دمج أو
نشر ضمن هذا الجرد.
